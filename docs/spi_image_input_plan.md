# SPI 图片输入分支方案

确认日期：2026-11-02。
基线：`ziguang_rv32i@15c1e4f`；新分支：`codex/spi-image-input`。
本文保留实现前的设计记录；实际实现、运行命令和验证边界见 [实现说明](spi_image_input.md)。

## 已确认的范围

- RK 发送 384×216 RGB888 图片，FPGA 硬件预处理到 96×96。
- 保留当前 99 任务 W8A16 检测网络、自己的双发射 Acore、DDR 和 SPI 通道。
- FPGA 对对应原图画最多 16 个框，经 PCIe 返回 384×216 RGB565。
- SPI 返回全部检测结果的类别、置信度、坐标和帧号。
- 第一阶段支持 RK 本地单张图片和图片目录循环；实测速度后再接视频。
- 继续保留原图/AI 两种输出选择。原图模式不运行预处理或推理。
- 新分支继续只维护根 `rv32I.pds`，原分支保留 HDMI 路线。

## 数据与存储

| 数据 | 每帧字节数 | 说明 |
| --- | ---: | --- |
| SPI 输入 RGB888 | 248832 | 按行，R/G/B 三字节，无压缩 |
| DDR 输入 RGBX8888 | 331776 | R/G/B/0，便于对齐与硬件逐像素读取 |
| 96×96 张量 | 294912 | INT16，HWC，通道补齐到 16 |
| PCIe 输出 RGB565 | 165888 | 10368 个 128-bit 数据字 |

RK 负责解码图片文件并统一到 384×216，FPGA 继续完成到 96×96 的均值缩小与张量格式化。
第一版沿用整幅图直接缩放，不增加 letterbox；框坐标按同一变换映射。
不在 SPI 上传 HWC 对齐后的大张量，也不在 FPGA 解码 JPEG/PNG。

模型包仍保留在 AI 逻辑 DDR 低 32 MiB，启动时上传并验证一次，之后逐帧复用。
建议输入缓冲固定在 AI 逻辑 `0x03e00000..0x03e51000`，与 `0x03f00000` 张量区分离。
原图继续使用现有视频槽布局，避免同时改 DDR 布局与 SPI 输入协议。

## 帧事务

1. 上传并验证模型（AI 模式）；此步骤不再以 HDMI/预处理就绪作为前提。
2. BEGIN：携带帧标识、尺寸、格式、总长度和整帧校验，取得输入缓冲所有权。
3. DATA：按已确认偏移上传 RGB888，每块经校验后写 DDR 并确认。
4. COMMIT：长度和整帧校验通过后，图片才成为可处理输入。
5. FPGA 从已上传的 DDR 图片产生可暂停的内部像素流，生成原图及所需张量。
6. AI 模式执行整网及后处理；原图模式跳过这两步。
7. FPGA 保留同帧原图并配置画框，RK 发起 PCIe DMA。
8. RK 核对帧号和完整数据长度后显示，再释放该帧并上传下一张。

SPI 不具有视频消隐语义：不能把包间停顿直接当成 DE 拉低。
因此先上传完整图片到 DDR，再由硬件按可控节奏读出，避免再次依赖外部 VS/DE。
分包可考虑 192 字节 RGB888（64 像素）对应 256 字节 DDR 写窗口；具体命令号在实现时统一分配。
复用现有包级 FNV-1a 校验和请求/应答流控，增加帧级长度、校验和所有权检查。
不自动重放结果不确定的写入；仅在已知偏移/内容校验的恢复协议下继续。

## 必须同步适配的实现

- 替换 HDMI 输入源、启动自检依赖及专用于 HDMI 的输入持有条件；保留有效输入检查。
- 为 DDR 图片读出增加有边界和背压的硬件输入通路，使用厂商存储/FIFO IP。
- 预处理支持 384×216：横向 4 像素、纵向自适应均值区间，保持明确的舍入规则。
- 重新核对张量跨域 FIFO 吞吐；不能直接沿用按每 20 像素出结果设计的 16-bit 串行写入速度。
- PCIe 读取长度、硬件框坐标、结果坐标和 RK 显示尺寸统一为 384×216。
- 输入、推理和发送期间禁止覆盖该帧；结果绑定模型会话、帧号及运行号。
- 新构建不依赖 HDMI 像素时钟、芯片配置或视频故障信号。
- 新的图片完成条件来自 COMMIT 和内部硬件处理，不通过伪造 HDMI 的成功状态实现。

## 阶段与验收

1. SPI 上传/校验与输入所有权；先验证 DDR 图片内容，尚不声称图像闭环通过。
2. 内部图片源、384×216 硬件预处理与原图 DDR 写入；定向检查边界和已知像素。
3. 384×216 原图 PCIe 回传及 RK 显示。
4. 模型运行、同帧画框、检测文字和目录循环。

分别计时上传、预处理、推理和 PCIe 接收，不用 SPI 标称频率推算整机 FPS。
优先短检查；模型算子不重复大规模回归。资源占用报告同时列用量和比例。
PDS 完整编译和烧录按用户后续安排，不在技术讨论阶段启动。

## 2026-11-03 源码核对后的设计细化

本节为实现前的细化方案；后续实现采用 DDR core 域内像素处理，具体以实现说明为准。

### 内部像素接口与完成条件

建议采用 `valid/ready + RGB + 帧首/行尾/帧尾` 的受控图片流，而不是为单张图片生成一套仿 HDMI 时序。
DDR 图片读出器、原图写入器和预处理共用该次图片事务；只有像素被接收时才推进像素坐标。
分流必须记录两路的接收状态，防止一路阻塞时另一条路径重复消费或漏像素。
RAW 模式只要求原图路径接收，AI 模式要求原图和预处理都消费同一帧。

- 输入读出先在 DDR core 域收完整突发，再通过厂商 FIFO 送至内部图片处理域。建议图片处理使用已有 25 MHz 时钟，不增加外部像素时钟。
- 紫光 DDR 读响应没有 `rready`；发 AR 前必须预留整个突发的缓冲，不能在返回中途依赖下游暂停 DDR。
- 行结束由第 384 个已接收像素产生，帧结束由第 82944 个已接收像素产生；SPI 包边界不参与行、帧划分。
- 原图写入、预处理结束和 DDR 落盘分开计数。RAW 必须确认 RGB565 共 165888 字节已写完；AI 还必须确认张量共 294912 字节已写完。
- 全部计数和 DMA 完成后才能发布有效帧；超时或取消产生的部分原图/张量不得发布。

现有 `ddr3_write_ctrl_lite.v` 在下一次 SOF 出现时发布上一帧完成，适合连续输入。
新 SPI 路径需要显式的单帧完成事件，在最后一个突发真正写完后发布，不能等待下一张图片或补发虚假图片。
现有 HDMI detector 还会将行首、行尾像素替换成 magic 标记；新受控输入建议以旁带信号携带边界，避免侵占真实图片像素。
DDR IP、原生突发握手和 PCIe 读出仍复用已有实现；原图槽的原生地址步长必须与读出侧一致。

### 384×216 预处理规则

沿用自适应均值池化的整数区间定义，输出仍是 96×96；不改变模型拓扑、任务表或量化参数。

```text
x_start = floor(ox * 384 / 96)
x_end   = ceil((ox + 1) * 384 / 96)
y_start = floor(oy * 216 / 96)
y_end   = ceil((oy + 1) * 216 / 96)
```

因此横向每格 4 像素，纵向每格 3 行，每格求 12 个像素的均值。
前四个纵向区间为 `[0,3)`、`[2,5)`、`[4,7)`、`[6,9)`，其后按周期推进；不是简单丢弃像素。
各通道均值继续使用 round-to-nearest, ties-to-even，再写为 INT16，通道顺序及补齐到 16 的规则保持现有模型输入约定。
源图先缩到 384×216 再预处理，与直接对 1080p 做一次均值缩小不保证逐像素相同，后续精度对比需要使用这条新的输入链。

当前 `hdmi_tensor_capture.v` 把 128-bit 输出拆成 8 次 16-bit FIFO 写入，一次输出像素有两个 128-bit 字。
原设计依赖输出像素间隔至少 20 个源时钟；384 宽时只隔 4 个源像素，不能直接更改尺寸常量。
建议改为厂商 128-bit 写、128-bit 读 FIFO，并让池化输出可反压；输入端也必须能暂停，完整处理均值计算流水线中的在途结果。
片上只保留突发和行累加所需缓冲，不把整张输入图展开为寄存器阵列。

### 命令与固件安排

保留现有模型上传、结果查询、RAW/AI 选择与 PCIe 展示命令；增加独立图片事务命令。
以下编号为设计预留，尚未写入 `comm_protocol.h`：

| 编号 | 建议命令 | 作用 |
| --- | --- | --- |
| 19 | IMAGE_STATUS | 查询新输入 ABI、固定尺寸/格式、状态、已提交字节数、帧号、详细错误与耗时 |
| 20 | IMAGE_BEGIN | 申请图片事务，登记会话、帧号、384×216、RGB888、248832 字节和整帧校验 |
| 21 | IMAGE_DATA | 指定会话、帧号、源字节偏移和 192 字节像素数据，确认 DDR 写入结果 |
| 22 | IMAGE_COMMIT | 校验整帧并排队硬件原图/张量生成；处理完成通过状态查询确认 |
| 23 | IMAGE_ABORT | 终止尚未处理的上传；硬件处理中只在安全边界撤销，不能清掉在途 DDR 命令 |

`COMM_NETWORK_RUN` 继续执行已生成张量的整网推理，`COMM_PRESENT_RUN` 继续发起原图或画框图回传。
`COMM_VIDEO_RELEASE` 在此分支适配为释放当前图片，不再自动进入 HDMI 等待/抓帧循环。
RK 启动时先查新 ABI，避免新客户端与旧 HDMI 固件混用。

第一版每块 192 字节 RGB888 对应 64 像素，CPU 打包为 256 字节 RGBX8888 写 DDR，可使用现有 256 字节 DDR 窗口。
整帧共有 1296 块。应答只在 DDR 完成并通过读回核对后推进已提交偏移。
整帧校验覆盖连续的全部 RGB 字节，不能直接调用会跳过包头第 12..15 字节的 `comm_hash` 来计算图片本体。
掉线后通过状态查询确定已提交偏移；第一版允许显式放弃重新上传，不自动重放结果不确定的命令。

固件上电只初始化 DDR/SPI 和状态机，等待模型或图片；模型上传不再等待 HDMI、预处理 HELD 或第一帧。
同一时间只允许一个图片事务。模型替换、输入覆盖、推理、展示和释放必须互相协调。
上传结束只表示输入图完整；原图完成、张量完成、推理完成和 PCIe 发送完成分别上报，便于定位故障。
结果用模型会话、图片会话、帧号和 run_id 绑定，RK 显示前核对同帧关系。

### 实际速度与后续视频输入

当前实际使用四线 50 MHz FSPI，理想净数据率为 25 MB/s；248832 字节仅像素在线路上约 9.95 ms。
这不包含命令、应答、CS 间隔、Linux ioctl、轮询、软核复制、DDR 核对或推理，不能据此承诺视频帧率。
现有传输固定 256 字节，一块数据至少有一次写请求和一次读应答；1296 块的这部分线路数据就有 663552 字节。
此外 `rk_control.c` 在空应答后等待 1 ms 再轮询，软核驱动按字节读写 INDEX/DATA；这两项需要在实测中单独观察。

第一版优先复用现有通信链，输出上传、预处理/存图、推理、后处理、PCIe/显示及端到端耗时。
若上传成为主要瓶颈，再使用硬件已有的 2048 字节容量或专用 FIFO/DMA 批量入 DDR；单纯增大包长不能消除 CPU 逐字节复制的开销。
接摄像头/视频后，RK 可以先只选择待处理帧并等待 FPGA 完成，不积压无限队列；需要并行吞吐时再增加双缓冲。
第一版不添加双缓冲和重叠推理，避免在输入链尚未验证时增加 DDR 竞争和跨帧错误。

### 里程碑

1. 图片上传与状态：验证少量固定块、整帧长度和校验，区分协议错误与 DDR 故障。
2. RAW 闭环：固定测试图 → SPI → DDR → FPGA RGB565 转换 → PCIe → RK 窗口，检查首尾像素、颜色和方向。
3. AI 闭环：接硬件预处理、现有模型、检测结果与最多 16 框叠加，核对帧号和框坐标。
4. 目录循环与性能：模型只上传一次，逐图显示和统计，之后再决定摄像头与批量上传优化。

只做针对新增协议、边界和像素格式的短检查，不重复运行完整模型长仿真。各可运行里程碑提醒提交 Git。
