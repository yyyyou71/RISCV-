# Acore 顺序双发射设计

## 范围与复用

在原 `rtl/Acore.v` 内增加 `ENABLE_DUAL`，默认 0。单发射保留原 PC、ROM 和冒险检测路径；
双发射使用取指队列和四操作数前递路径。主槽 A 沿用原译码、执行、访存、写回和乘除法控制。
副槽 B 再例化一份原 `decoder` 和 `ALU`，使用同一个架构寄存器堆。
原 `CSR.v`、`branch_predictor.v`、`multiply_unit.v`、`divide_unit.v`、`decoder.v` 和 `ALU.v`
均保持实现不变。数据总线仍只支持每拍一次访存。没有引入 Cache、寄存器重命名、ROB 或乱序调度。

## 发射规则

队头是较老指令 A，紧邻 PC+4 的指令是候选 B。两条同时满足以下条件才一起取出：

- 都属于合法编码的普通整数 OP / OP-IMM、LUI 或 AUIPC。
- A 的非零目的寄存器不是 B 实际使用的源寄存器，即没有同组 RAW。
- 两条不写同一个非零目的寄存器，即没有同组 WAW。
- 当前第一条没有预测跳转，队列中有两条连续指令。

不满足时只取出 A，B 留在队头，下一次作为 A 尝试执行；不能跳过 B 去找后面的独立指令。
访存、分支、JAL/JALR、CSR/MRET、FENCE、乘除法都独占一组。
WAR 可以成对执行，因为两个操作数先从旧架构状态读取，结果在后面一起写回。
x0 不参与写相关；LUI/AUIPC 没有 GPR 源，立即数字段不会被误判为源寄存器。

例如 `addi x5,x1,1; addi x6,x2,2` 可以成对；`addi x5,x1,1; add x6,x5,x2` 拆成两组。
本版没有 A 当拍计算结果再送 B 的组合旁路，避免两级 ALU 串联拉长关键路径。

## 取指与存储器

新增 `acore_fetch_queue.v`，容量八条，包含指令、PC 和预测元信息。
`pango_acore_fetch` 是 8192×32 的真双口 DRM IP，两个写口均接 0；
同一时钟下分别读取 PC 和 PC+4，输出寄存器关闭，原生同步读取一拍。
容量仍是 32 KiB，并非复制两份 ROM。以双口 RAM IP 实现只读程序存储器，是为了获得两个独立读地址。

队列允许一次消耗一条或两条。发请求前预留正在返回的最多两条指令所需空间，
因此执行端因 load-use 或乘法停顿时，取指端只填满队列，不覆盖尚未执行的指令。
请求在一拍后得到 IP 数据，再写进队列，所以首次取指额外经过队列接收；稳定状态可以每拍接收两条。
跳转纠错、中断和 MRET 同时清空队列及 pending 标志，旧请求即使返回也不会被执行。
允许目标 PC 的 bit2 为 1，直接用两个端口读取该字及下一字，不要求八字节对齐。

继续使用原分支预测器：每次请求只查询首个 PC。若首条预测跳转，只入队首条并从预测目标继续请求；
第二条的预测标记为未跳转，它作为 A 执行分支时仍由原 EX 纠错逻辑处理。
这是控制复杂度和预测覆盖率之间的取舍，并不保证分支预测性能与单发射完全相同。

数据 RAM 仍为 64 KiB、Transparent_Write、CPU 仅用 A 口。
双发射的 `pango_acore_ram` 和 `acore_dual_*.hex` 与单发射初始化文件隔离。
ROM 0x00000000、RAM 0x00010000、MMIO 0x00030000 段均沿用原地址图。

## 寄存器堆与前递

`GPR_matrix.v` 扩为四读两写。仍只有 31×32 bit 的架构数据，x0 固定为零；
增加的是读选择器、写译码和每个寄存器的写数据选择器，而不是复制一套架构寄存器。
单发射参数会裁掉副槽端口。防御性写入优先级为 B，但同组 WAW 已在发射时禁止。

`acore_forward.v` 对四个实际源寄存器分别选取最近的较老生产者：

1. 紧前一组的 B 结果。
2. 紧前一组的 A 结果。
3. 写回组的 B 结果。
4. 写回组的 A 结果。
5. 寄存器堆。

阶段优先于槽位：新 A 必须盖过旧 B。若最近匹配是尚未完成读取的 load，
整组停顿，不能绕过这个 load 去取更旧的同名寄存器值。
本版访存独占一组，B 的结果永远是已就绪的整数结果。
第二槽也能向下一组的 A/B 前递；主槽的 store 数据、CSR 操作数和乘法操作数同样看到副槽结果。

## 停顿、写回和中断

两个槽共用组级停顿。任一真实源遇到 load-use 等待时，ID/EX 两槽一起保持，
EX/MEM 注入空泡，较老组继续排空。乘除法仍使用原 busy/ready 协议并独占当前组。
副槽结果、目的寄存器和 valid 依次经过 EX/MEM 和 MEM/WB，与主槽同组同时写回。

原 decoder 把 valid_in=0 当作 kill。取指队列可能暂时为空，因此双发射停顿期间，
输入 valid 必须反映正在保持的执行槽，不能用已经变空的队头 valid 覆盖它；否则会丢掉等待中的指令。
这项处理只在 `ENABLE_DUAL=1` 时启用。

中断在可推进的有效 EX 指令组边界接受。当前组的 A/B 均继续完成，年轻组被冲刷。
如果队列已有下一条，mepc 保存它的 PC；否则顺序后继取 PC+8（双槽）或 PC+4（单槽），
实际跳转则保存跳转目标。CSR/MRET 独占，避免同沿 CSR 配置与进入中断争用状态。
没有增加同步异常架构；总线错误仍沿用原板级错误指示。

## 调试与验证

内核保留仿真提交探针和计数器，板级未连接时由综合裁掉，不新增 MMIO 或引脚。
CoreMark 仿真统计与 C 计时完全相同的两次周期计数器读取之间的退休指令数和副槽数。

- `scripts/test_acore_dual.py`：四组固定种子的随机程序，同时执行单/双发射；
  按程序顺序逐条比较提交 PC、机器码、目的寄存器和值，最后比较 65536 字节 RAM。
  包含整数运算、符号/无符号移位比较、x0、跨组覆盖、load-use、字节写、乘法、循环和跳转冲刷。
- `scripts/test_acore_dual_interrupt.py`：CSR、双槽边界、双槽 load-use、乘除法等待、
  分支、JAL/JALR 和 MMIO 中断；服务程序破坏 GPR 后检查全部现场恢复。
- `scripts/test_interrupt.py`：原单发射完整回归。
- `scripts/check_modelsim.py --core acore_dual`：官方程序/数据存储器、字节写掩码、
  乘法 IP 与两组标准 CoreMark CRC。
- `scripts/check_verilator.py --core acore_dual --require-duration`：最终 1000 次固件，
  解码真实 UART 比特流，确认 CRC、结束状态、计时不少于十秒及副槽确实退休。
- `scripts/build_acore_dual.ps1`：依次运行上述检查、PDS 实现、四角 setup/hold 审计、位流发布和 GUI 工程导出。

这是保守的第一版。访存和控制指令占比、数据依赖及乘法阻塞仍限制 IPC；
“每周期最多两条”不等于 CoreMark 或所有程序提升两倍。
后续可单独评估“一条访存加一条独立 ALU”的收益，但需要增加访问故障与两槽取消规则的验证。

## 本机实现结果（2026-10-28）

最终 performance 1000 次：353866975 周期，14.154679 秒，2.82592067 CoreMark/MHz；
计时窗口退休 309852378 条，其中副槽 57887831 条，IPC 0.87561824。
此前单发射基线为 2.64330050 CoreMark/MHz，本版整体提升约 6.9%，包含取指前端变化的影响。
两组标准 CRC、24082 条提交的随机对比、14 项双发射 CSR/中断测试及原 16 项中断回归通过。

实现使用 5551 LUT、5442 FF、4 APM、24 DRM36K，分布式 RAM 为 0。
最终独立 STA：slow setup +19.600 ns、hold +0.163 ns；fast setup +27.484 ns、hold +0.031 ns。
40 ns 周期和 0.2 ns 时钟不确定度保持原值，两个角均为零违例端点。

PDS 路由修复日志包含 `Hold violation fix failed`，并打印最终 slow/fast hold 为 163/31 ps。
本次配置的修复目标为 200 ps；修复后摘要和最终独立 STA 均明确给出正 slack 与 `All Constraints Met`。
审计同时检查两份报告的四组结果，不依据“成功生成位流”判断时序通过；原始日志保留在 build 下。
